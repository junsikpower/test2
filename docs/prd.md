# 뽀모도로 타이머 겸 작업 기록 웹앱 — Product Requirements Document (PRD) v4 (Final)

## 1. Project Overview

### 1.1 Project Definition
브라우저에서 파일 하나로 실행되는 완전 로컬형 뽀모도로 타이머 겸 작업 기록 웹앱으로, 서버나 인터넷 연결 없이 뽀모도로 집중/휴식 사이클을 운영하고 세션별 작업 메모와 일별 완료 기록을 관리하는 도구.

### 1.2 Background
사용자는 별도 설치나 서버 구축 없이, 브라우저에서 파일을 열기만 하면 즉시 사용할 수 있는 개인용 생산성 도구를 필요로 한다. 특히 장시간 사용 시에도 타이머 정확도가 보장되고, 새로고침이나 재접속에도 데이터가 유지되는 신뢰성이 핵심 요구사항이다.

### 1.3 Target Environment
- 웹 브라우저 (로컬 HTML 파일을 직접 열어 실행, `file://` 프로토콜)
- 서버/백엔드 없음 (Serverless, 완전 클라이언트 사이드)
- 인터넷 연결 불필요 (완전 오프라인 동작)
- **지원 브라우저**: Chrome, Edge, Firefox 최신 데스크톱 버전에서 `file://` 프로토콜로 직접 실행하는 환경을 기준으로 하며, 해당 환경에서 `localStorage` 기반 데이터 지속성을 **최선 노력(best-effort) 기준으로 지원**한다. 브라우저 정책·저장 공간 등으로 실제 쓰기가 실패하는 경우의 처리는 EC-05에 정의한다. `file://` 환경에서 localStorage 접근 자체가 차단되는 브라우저(예: 구형 Safari 등)는 지원 범위에서 제외한다.

## 2. Goals & Success Definition

### 2.1 Project Goals
- 뽀모도로 기법 기반 집중/휴식 사이클을 정확하게 운영한다.
- 세션별 작업 내용을 기록하고 일별로 조회 가능하게 한다.
- 장시간·오프라인 환경에서도 안정적으로 동작한다.

### 2.2 Goal Completion State
- 사용자가 파일을 열면 즉시 타이머를 시작/일시정지/리셋할 수 있는 상태
- 집중 세션이 정상 종료되면 완료 카운트가 증가하고 메모 입력 대기 상태로 전환되며, 사용자가 메모를 제출하거나 건너뛰면 다음 세션(짧은 휴식/긴 휴식)의 타이머가 자동으로 시작되는 상태 (단, 이 자동 시작은 사용자가 실시간으로 앱을 사용 중인 경우에 한한다 — BR-02)
- 짧은 휴식·긴 휴식이 정상 종료되면 별도 입력 없이 다음 Focus 세션이 자동으로 시작되는 상태 (동일하게 BR-02 적용)
- 로그 화면에서 하루 단위 완료 개수와 메모 목록을 확인할 수 있는 상태
- 설정 화면에서 집중/짧은휴식/긴휴식 시간을 변경하면, Idle 상태인 세션에는 즉시 반영되고 Running/Paused 상태인 세션에는 해당 세션 종료 이후부터 반영된 상태 (FR-07)
- 앱이 다시 실행되는 시점(새로고침·재접속)을 기준으로 진행 중이던 타이머, 설정값, 로그가 정상 복원된 상태

### 2.3 Overall Success Conditions
- 인터넷 연결 없이 파일을 여는 것만으로 모든 기능이 정상 동작한다.
- 브라우저가 실행 중인 동안, 수 시간 이상 타이머를 켜두어도 표시 시간과 실제 경과 시간 간 오차(밀림)가 발생하지 않는다.
- 브라우저를 껐다 켜거나 새로고침해도, 앱이 다시 실행되는 시점을 기준으로 설정·로그·진행 중이던 세션 상태가 정상 복원된다.
- 단, 브라우저가 완전히 종료되어 있던 동안 만료된 세션의 알림은 실시간으로 발생할 수 없으며, 앱이 다시 실행되는 시점에 종료 처리된다(EC-03 참고). 이 경우 다음 세션은 자동 시작되지 않고 Idle로 대기한다(BR-02).
- localStorage 쓰기가 실패하는 동안에도 앱의 사용 자체는 중단되지 않으며, 사용자는 저장 실패 사실을 인지할 수 있다(EC-05).

## 3. Scope

### 3.1 In Scope
- 25분 집중 타이머 시작/일시정지/리셋 (기본값: 집중 25분 / 짧은휴식 5분 / 긴휴식 15분)
- 집중 세션 종료 시 소리 및 브라우저 알림(권한 허용 시 동시 발송)
- 뽀모도로 사이클 자동 전환 (Focus ↔ Short Break, 4번째 Focus 슬롯 소모 후 Long Break)
- 현재 세션을 건너뛰고 다음 세션으로 즉시 이동하는 스킵 버튼
- 집중 세션 종료 시 한 줄 작업 메모 입력(빈 값·건너뛰기 허용)
- 하루 단위 완료 뽀모도로 개수 및 메모 목록(오름차순)을 보여주는 로그 화면
- 설정 화면에서 집중/짧은휴식/긴휴식 시간 직접 변경(1~180분 정수, 유효성 검증 포함)
- 새로고침·재접속 시에도 유지되는 데이터 영속성 및 저장 실패 시 사용자 고지
- 완전 오프라인 동작 (단일 HTML 파일, 외부 리소스 미사용)
- 장시간 구동 시에도 시간 오차 없는 타이머 정확도(시스템 시계 정상 유지 조건 하)
- 지원 브라우저: Chrome/Edge/Firefox 최신 데스크톱 버전(`file://` 실행 기준)
- 세부 디자인 및 UI는 Development AI 재량으로 결정

### 3.2 Out of Scope / Non-goals
- Chrome, Edge, Firefox 최신 데스크톱 버전 외의 브라우저(Safari 등)에서의 정상 동작 보장
- 브라우저/OS 설정으로 인해 Notification API가 실제 화면에 알림을 표시하지 않는 경우의 감지·보정 (JS로 감지 불가능한 영역 — FR-02 참고)

## 4. Functional Requirements

### FR-01. 타이머 시작/일시정지/리셋

**Purpose / Rationale**
- 사용자가 집중/휴식 세션의 진행을 직접 제어할 수 있도록 한다.

**Trigger**
- 사용자가 시작/일시정지/리셋 버튼을 클릭

**Input**
- 버튼 클릭 이벤트, 현재 세션 타입 및 설정된 세션 길이

**Processing / Business Rules**
- 시작: 현재 시각 기준으로 종료 목표 시각(endTimestamp = 현재시각 + 남은시간)을 계산하여 저장하고 세션 상태를 Running으로 전환
- 일시정지: 남은 시간을 고정하여 저장하고 세션 상태를 Paused로 전환
- 리셋: 현재 세션의 타이머만 설정된 길이의 Idle 상태로 되돌린다. 사이클 내 소모된 Focus 슬롯 수는 리셋의 영향을 받지 않고 그대로 유지된다(BR-03).
- 시작/일시정지/리셋 버튼은 Focus/Short Break/Long Break 세션이 Idle, Running, Paused 상태일 때만 노출된다. `Memo-Input-Pending` 상태에서는 이 버튼들이 노출되지 않는다(BR-04).

**Output**
- 화면에 갱신된 남은 시간 표시, 버튼 상태(시작/일시정지) 전환

**Expected State**
- 타이머가 사용자의 조작에 따라 Running/Paused/Idle 상태 중 하나로 정확히 반영되며, 사이클 진행도(소모된 Focus 슬롯 수)는 리셋과 무관하게 보존됨

**Acceptance Criteria**
- 시작 후 임의 시점에 표시되는 남은 시간이 실제 경과 시간과 일치한다.
- 일시정지 후 남은 시간이 변하지 않는다.
- 리셋 시 설정된 세션 길이의 Idle 상태로 정확히 복귀한다.
- 3번째 Focus 슬롯까지 소모된 상태에서 4번째 Focus를 리셋해도, 슬롯 소모 수는 3으로 유지된다.
- `Memo-Input-Pending` 상태에서는 시작/일시정지/리셋 버튼이 화면에 나타나지 않는다.

### FR-02. 세션 종료 알림

**Purpose / Rationale**
- 집중/휴식 세션이 끝났음을 사용자에게 즉시 알려 흐름이 끊기지 않게 한다.

**Trigger**
- 진행 중인 세션의 남은 시간이 0에 도달

**Input**
- 타이머의 종료 목표 시각과 현재 시각의 비교 결과

**Processing / Business Rules**
- Notification 권한이 허용된 경우, 소리 알림(Web Audio API 합성음)과 브라우저 알림(Notification API)을 항상 동시에 발송한다(택일이 아님).
- Notification 권한이 거부되었거나 Notification API 자체를 지원하지 않는 경우, 소리 알림과 탭 제목 변경으로 대체한다(EC-01).
- **소리 알림은 브라우저 알림 권한 상태와 무관하게 항상 재생을 시도하는 주(主) 알림 수단이다.** Notification API 호출이 성공(권한 허용, 표시 함수 정상 호출)해도 OS/브라우저 설정에 의해 실제 화면에 알림이 표시되지 않을 수 있으나, 이는 JavaScript로 감지할 수 없는 영역이므로 별도 감지·보정을 하지 않는다(3.2). 반면 오디오 재생 실패는 `play()` 호출의 Promise 거부로 감지 가능하므로, 실패 시 탭 제목 변경으로 즉시 대체한다.
- 브라우저의 오디오 자동재생 제한을 회피하기 위해, 사용자가 앱과 최초로 상호작용(예: 시작 버튼 클릭)하는 시점에 오디오 컨텍스트를 활성화한다(세부 구현은 12.3에 따라 Development AI 재량)

**Output**
- 알림음 재생, (권한 허용 시) 데스크톱 알림 표시 시도, (권한 거부/미지원 시) 탭 제목 변경

**Expected State**
- 앱이 실행 중인 동안, 사용자가 다른 작업 중이어도 세션 종료 사실을 인지할 수 있는 상태

**Acceptance Criteria**
- 앱이 실행 중인 동안에는 세션 종료 시점에 알림이 지체 없이 발생한다.
- 권한이 허용된 경우 소리 재생과 브라우저 알림 호출이 함께 발생한다.
- 오디오 재생이 실패로 감지되면 탭 제목 변경으로 대체된다.

### FR-03. 뽀모도로 사이클 자동 전환

**Purpose / Rationale**
- 뽀모도로 기법의 집중-휴식 리듬을 사용자 개입 없이 자동으로 유지한다.

**Trigger**
- 진행 중이던 세션이 정상 종료(시간 만료)되었을 때

**Input**
- 현재 세션 타입, 사이클 내 소모된 Focus 슬롯 수

**Processing / Business Rules**
- Focus 세션이 정상 종료되면: (1) 완료 카운트를 1 증가 → (2) 세션 상태를 `Focus 완료 + Memo-Input-Pending`으로 전환(이 상태에서는 다음 세션의 타이머가 시작되지 않음) → (3) 사용자가 메모를 제출하거나 건너뛰면 BR-01 순서에 따라 다음 세션이 결정되어 자동으로 카운트다운을 시작
- Short Break 또는 Long Break가 정상 종료되면: 메모 절차 없이 곧바로 다음 Focus 세션이 자동으로 카운트다운을 시작
- 완료 카운트 증가와 Focus 슬롯 소모 처리 간의 저장 순서 등 내부 데이터 저장 세부사항은 12.3 Implementation Freedom에 따라 Development AI가 결정한다.

**Output**
- 다음 세션 타입과 길이로 초기화되어 자동 시작된 타이머 화면

**Expected State**
- 사용자 개입 없이 BR-01 규칙에 따라 정확한 다음 세션으로 자동 진입한 상태

**Acceptance Criteria**
- 4번째 Focus 슬롯이 소모된 직후에는 반드시 Long Break로 전환된다.
- 그 외 Focus 종료 시에는 Short Break로 전환된다.
- Break 세션 종료 후에는 메모 입력 없이 곧바로 다음 Focus가 시작된다.

---

### FR-04. 세션 건너뛰기 (Skip)

**Purpose / Rationale**
- 사용자가 현재 세션을 즉시 종료하고 다음 세션으로 넘어갈 수 있도록 한다.

**Trigger**
- 사용자가 스킵 버튼 클릭

**Input**
- 버튼 클릭 이벤트, 현재 세션 타입

**Processing / Business Rules**
- 현재 세션을 미완료 상태로 즉시 종료하고 BR-01 순서에 따라 다음 세션으로 자동 전환·시작
- 스킵된 세션이 Focus였던 경우, 완료 카운트를 증가시키지 않고 메모 입력도 요구하지 않는다. 다만 사이클 내 Focus 슬롯은 소모된 것으로 계산되어 Long Break 도달 순서에는 정상 반영된다.
- 스킵 버튼은 Focus/Short Break/Long Break가 Idle, Running, Paused 상태일 때만 노출된다. `Memo-Input-Pending` 상태에서는 스킵 버튼이 노출되지 않는다(BR-04) — 이 상태는 메모 제출/건너뛰기로만 벗어날 수 있다.

**Output**
- 다음 세션 타입과 길이로 초기화되어 자동 시작된 타이머 화면

**Expected State**
- 스킵된 세션은 로그에 기록되지 않되, 사이클 순서(슬롯 소모)는 정상 진행된 상태

**Acceptance Criteria**
- 스킵 직후 로그의 완료 개수가 변하지 않는다(Focus 스킵 시).
- Focus를 2회 스킵한 뒤 정상 완료를 2회 채우면, 총 4개의 Focus 슬롯이 소모되어 Long Break로 전환된다(완료 카운트는 2로 기록됨).
- `Memo-Input-Pending` 상태에서는 스킵 버튼이 나타나지 않는다.

---

### FR-05. 작업 메모 기록

**Purpose / Rationale**
- 각 집중 세션에서 수행한 작업을 짧게 기록하여 이후 조회할 수 있게 한다.

**Trigger**
- Focus 세션이 정상 종료(시간 만료)되었을 때

**Input**
- 사용자가 입력하는 한 줄 텍스트(제출 또는 건너뛰기)

**Processing / Business Rules**
- 사용자는 메모를 제출하거나 건너뛸 수 있다. 빈 값(공백 또는 미입력) 제출과 건너뛰기 모두 허용되며, 두 경우 모두 완료 카운트는 정상 반영되고 메모 텍스트만 빈 값으로 저장된다. 별도의 '취소' 동작은 없다(제출 또는 건너뛰기 중 하나로만 대기 상태를 벗어남).
- 저장된 메모는 완료 시각과 함께 해당 날짜의 로그 데이터에 추가된다.

**Output**
- 로그 화면에 반영되는 메모 항목(빈 값일 경우 '메모 없음'으로 표시)

**Expected State**
- 해당 Focus 세션의 완료 기록과 메모(또는 빈 메모)가 하루 단위 로그에 귀속된 상태

**Acceptance Criteria**
- Focus 세션이 정상 종료될 때마다 메모 입력 창이 표시된다.
- 빈 값 제출 또는 건너뛰기를 선택해도 완료 카운트는 정상 증가한다.

---

### FR-06. 일별 로그 화면

**Purpose / Rationale**
- 사용자가 하루 동안의 생산성(완료한 뽀모도로 개수)과 수행 내역(메모)을 한눈에 파악할 수 있도록 한다.

**Trigger**
- 사용자가 로그 화면으로 이동

**Input**
- 저장된 날짜별 로그 데이터

**Processing / Business Rules**
- 선택된 날짜(기본값: 오늘)의 완료된 뽀모도로 개수와 메모 목록을 오름차순(시간순, 오래된 순)으로 정리하여 표시한다.
- 모든 시각은 사용자 기기의 로컬 타임존을 기준으로 한다.

**Output**
- 날짜별 완료 개수 및 메모 리스트 UI

**Expected State**
- 로그 화면이 항상 실제 저장된 데이터와 일치하는 상태

**Acceptance Criteria**
- 표시되는 완료 개수가 해당 날짜에 정상 종료된 Focus 세션 수와 정확히 일치한다.
- 메모가 오래된 순으로 정렬되어 표시된다.

---

### FR-07. 설정 (세션 길이 커스터마이징)

**Purpose / Rationale**
- 사용자가 자신의 작업 스타일에 맞게 세션 길이를 조정할 수 있도록 한다.

**Trigger**
- 사용자가 설정 화면에서 값을 변경하고 저장

**Input**
- 집중시간/짧은휴식/긴휴식 각각의 사용자 입력 값(분 단위)

**Processing / Business Rules**
- 기본값은 집중 25분 / 짧은휴식 5분 / 긴휴식 15분이다.
- 입력값은 1분 이상 180분 이하의 정수만 허용하며, 범위를 벗어나거나 소수·비숫자가 입력되면 저장을 막고 오류를 표시한다.
- **적용 시점**: 설정 저장 시점에 해당 세션 타입이 **Idle 상태**라면(아직 시작되지 않았으므로) 화면 표시와 다음 시작 시 사용할 길이가 **즉시** 새 값으로 갱신된다. 해당 세션 타입이 **Running 또는 Paused 상태**라면 변경된 값은 그 세션에는 적용되지 않고, 해당 세션이 종료된 이후 같은 타입의 세션부터 적용된다.

**Output**
- 갱신된 설정값이 반영된 타이머 화면(Idle 세션은 즉시, 진행 중 세션은 다음 회차부터)

**Expected State**
- Idle 상태의 세션은 새 설정값을 즉시 표시하고, Running/Paused 상태의 세션은 기존 길이를 유지한 채 종료 후부터 새 값을 따르는 상태

**Acceptance Criteria**
- 설정 화면에서 값을 변경하고 저장하면, 새로고침 후에도 변경된 값이 유지된다.
- 범위를 벗어난 값(0 이하, 181 이상, 소수, 비숫자)은 저장되지 않는다.
- 현재 Focus가 Idle 상태에서 설정을 변경하면, 화면의 Focus 남은시간 표시가 즉시 새 값으로 바뀐다.
- 현재 Focus가 Running 또는 Paused 상태에서 설정을 변경하면, 그 세션은 기존 길이로 계속 진행되고 다음 Focus 세션부터 새 값이 적용된다.

---

### FR-08. 데이터 영속성 및 상태 복원

**Purpose / Rationale**
- 새로고침이나 브라우저 재시작 후에도 사용자의 진행 상황과 데이터를 잃지 않도록 한다.

**Trigger**
- 페이지 로드(새로고침 또는 재접속)

**Input**
- localStorage에 저장된 설정/로그/진행 중 타이머 상태 데이터

**Processing / Business Rules**
- 저장된 설정값, 로그, 진행 중이던 타이머의 세션 타입·세션 상태·사이클 내 소모된 Focus 슬롯 수를 그대로 복원한다.
- **Running 상태로 저장된 세션**: 저장된 종료 목표 시각(endTimestamp)과 현재 시각을 비교하여 만료 여부를 판단한다. 이미 종료된 경우, 오프라인 기간 동안 몇 번의 세션이 경과했는지와 무관하게 '중단 시점의 세션 1회만' 종료 처리한 뒤 다음 세션을 Idle 상태로 대기시킨다(사용자가 직접 시작, BR-02). 아직 남아 있다면 남은 시간을 그대로 이어서 표시한다.
- **Paused 상태로 저장된 세션**: `endTimestamp`가 존재하지 않으므로 만료 여부를 판단하지 않는다. 저장된 남은 시간 스냅샷과 Paused 상태를 그대로 복원하며, 오프라인 기간이 얼마였든 남은 시간은 변하지 않는다(일시정지 중에는 시간이 흐르지 않으므로).
- 완료 처리된 세션의 로그 귀속 날짜는 원래의 종료 목표 시각(endTimestamp) 기준 날짜로 기록한다.

**Output**
- 복원된 타이머 화면, 설정 화면, 로그 화면

**Expected State**
- 새로고침/재시작 전후 사용자 관점에서 데이터 손실이나 진행 상황 단절이 없는 상태

**Acceptance Criteria**
- 임의 시점에 새로고침해도 타이머 진행 상태(남은 시간 포함), 설정값, 로그가 새로고침 이전과 동일하게 유지된다.
- 여러 세션이 경과한 뒤 재접속해도 완료 처리는 1회로 제한되고, 그 세션의 로그는 원래 종료 목표 시각 기준 날짜에 기록된다.
- 복원 후 다음 세션은 자동으로 시작되지 않고 Idle 상태로 대기하며, 사용자의 시작 조작을 필요로 한다.
- Paused 상태에서 새로고침한 경우, 오프라인 시간과 무관하게 남은 시간 스냅샷이 그대로 복원되며 종료 처리되지 않는다.

## 5. Business / System Rules

### BR-01. 세션 순서 및 완료 카운트 규칙
- 세션은 Focus → Short Break → Focus → Short Break → Focus → Short Break → Focus → Long Break 순서로 반복되며, Long Break 이후 다시 Focus부터 사이클이 재시작된다. Long Break가 스킵된 경우에도 동일하게 사이클이 초기화되어 Focus부터 재시작된다.
- 사이클 내 Focus 슬롯(1~4번째)은 완료·스킵 여부와 무관하게 소모되며, 4번째 Focus 슬롯이 소모되면 Long Break로 전환된다.
- 하루 단위 완료 개수(로그 표시용)는 정상적으로(시간 만료로) 종료된 Focus 세션에 대해서만 1씩 증가한다. 스킵된 Focus는 완료 개수에 포함되지 않는다.
- 스킵 버튼은 Focus, Short Break, Long Break 모든 세션 타입에서 사용 가능하다(단, BR-04에 따라 `Memo-Input-Pending` 상태는 제외).

### BR-02. 자동 시작의 적용 범위
- 세션 종료 후 다음 세션의 자동 시작(FR-03)은 **사용자가 실시간으로 앱을 사용 중인 상황에서만** 적용되는 원칙이다.
- 앱이 장시간 비활성 상태였다가 재개된 경우 — 즉 새로고침·재접속으로 인해 이미 만료된 세션을 복원하는 경우(FR-08, EC-03) — 에는 다음 세션을 자동으로 시작하지 않고 Idle 상태로 대기시켜, 사용자가 실제로 자리에 복귀했음을 스스로 확인한 뒤 다음 세션을 직접 시작하도록 한다.
- 이는 사용자가 인지하지 못한 채로 세션(특히 Focus)이 자동 진행되어 소모되는 것을 방지하기 위함이다.

### BR-03. 리셋(Reset)과 사이클 슬롯의 독립성
- 리셋(FR-01)은 현재 진행 중인 세션의 타이머만 초기화하며, 사이클 내 소모된 Focus 슬롯 수(사이클 진행도)에는 영향을 주지 않는다.
- 즉, 리셋 후에도 사이클 진행 단계(몇 번째 Focus 슬롯까지 소모되었는지)는 리셋 이전 상태로 유지된다.

### BR-04. Memo-Input-Pending 상태의 조작 제한
- `Memo-Input-Pending` 상태에서는 타이머 제어 버튼(시작/일시정지/리셋/스킵)이 화면에 노출되지 않는다.
- 이 상태에서 노출되는 조작은 메모 제출과 메모 건너뛰기(FR-05) 두 가지뿐이며, 둘 중 하나를 수행해야만 이 상태를 벗어나 다음 세션으로 진입한다.
- 이는 다음 세션이 아직 결정·시작되지 않은 과도기 상태에서 사용자가 타이머를 조작해 상태 머신이 꼬이는 것을 방지하기 위함이다.

## 6. State & Data Model

### 6.1 System / UI States
- Focus-Idle / Focus-Running / Focus-Paused
- Short Break-Idle / Short Break-Running / Short Break-Paused
- Long Break-Idle / Long Break-Running / Long Break-Paused
- Memo-Input-Pending (Focus 세션 정상 종료 후 메모 입력 대기 — 이 상태에서는 다음 세션의 타이머가 아직 시작되지 않으며, 타이머 제어 버튼도 노출되지 않는다. 메모 제출/건너뛰기 UI만 노출된다 — BR-04)
- Settings (설정 화면)
- Log (로그 화면)

### 6.2 Data States
- 진행 중 타이머 상태: **존재(Active)**는 TimerState의 세션 상태가 Running 또는 Paused인 경우를, **없음(None)**은 세션 상태가 Idle인 경우를 의미한다. 즉 Active/None은 6.1의 Running/Paused와 Idle을 각각 상위 개념으로 묶어 부르는 것이며 1:1로 대응한다.
- `Memo-Input-Pending`은 이전 Focus 세션이 이미 완료·종료되고 다음 세션은 아직 시작되지 않은 시점의 별도 UI 오버레이 상태다. 이 시점의 기저 TimerState 세션 상태는 Idle(즉, 데이터 상태는 None)이다.
- 설정값 상태: 기본값 / 사용자 변경값
- 일별 로그 상태: 데이터 없음(해당 날짜에 완료 기록 없음) / 데이터 존재
- 저장소 상태: 정상(Synced) / 쓰기 실패(Write-Failed, EC-05)

### 6.3 Core Data Entities

**TimerState**
- 세션 타입 (Focus / ShortBreak / LongBreak)
- 세션 상태 (Idle / Running / Paused)
- 종료 목표 시각 (endTimestamp, Running 상태일 때만 유효, 로컬 타임존 기준)
- 남은 시간 스냅샷 (Paused 상태일 때만 유효 — 정의상 항상 1초 이상의 양수 값을 가진다. 남은 시간이 0에 도달하는 순간은 Running 상태에서만 발생하며, 그 즉시 세션 종료 처리로 전이하므로 Paused로는 진입하지 않는다)
- 사이클 내 소모된 Focus 슬롯 수 (0~4)
- 시계 이상 감지용 앵커: 마지막으로 갱신된 `dateAnchor`(Date.now() 값)와 `perfAnchor`(performance.now() 값) — EC-04 참고

**Settings**
- 집중시간 길이(분), 기본값 25
- 짧은휴식 길이(분), 기본값 5
- 긴휴식 길이(분), 기본값 15
- (공통) 허용 범위: 1~180분 정수

**DailyLog**
- 날짜 (로컬 타임존 기준)
- 완료된 뽀모도로 개수
- 메모 목록 (각 항목: 완료 시각, 메모 텍스트 — 빈 값 허용)

## 7. Data Lifecycle & Persistence

### 7.1 Data Ownership
- 모든 데이터는 사용자의 로컬 브라우저 환경에 귀속되며, 외부 서버로 전송되지 않는다.

### 7.2 Storage
- localStorage를 사용하며, 설정 / 일별 로그 / 진행 중 타이머 상태를 각각 별도의 키로 분리하여 저장한다.
- 지원 브라우저(Chrome/Edge/Firefox 최신 데스크톱 버전)에서 `file://` 프로토콜로 직접 실행 시의 localStorage 동작을 최선 노력 기준으로 지속성 지원 대상으로 하며, 쓰기 실패 시의 동작은 EC-05를 따른다.

### 7.3 Synchronization
- 서버가 존재하지 않으므로 로컬-서버 간 동기화는 발생하지 않는다.

### 7.4 Retention
- 별도의 만료 기한 없이, 사용자가 브라우저 저장소 데이터를 직접 삭제하기 전까지 보존된다.

### 7.5 Deletion
- 사용자가 브라우저의 사이트 데이터/캐시를 삭제할 경우 설정, 로그, 진행 중 타이머 상태가 모두 함께 소실된다.
- 앱 자체 내에는 별도의 데이터 삭제 기능이 요구사항으로 승인되지 않았다.

## 8. Error & Edge Cases

### EC-01. 브라우저 알림 권한 거부 또는 Notification API 미지원
- 발생 조건: 사용자가 Notification API 권한 요청을 거부했거나, 브라우저가 Notification API 자체를 지원하지 않는 경우
- 시스템 상태: 브라우저 알림 발송 불가
- 사용자에게 표시되는 결과: 소리 알림과 탭 제목 변경으로 세션 종료를 알림
- 데이터 처리: 영향 없음
- 재시도/복구/롤백 정책: 별도 재요청 없이 매 세션 종료 시 폴백 수단으로 대체
- 최종 상태: 앱이 실행 중인 동안, 사용자가 최소 하나의 알림 수단으로 세션 종료를 인지할 수 있는 상태
- 참고: 권한이 허용되고 API 호출이 성공해도 OS/브라우저 설정으로 실제 알림이 표시되지 않는 경우는 감지·보정 대상에서 제외한다(3.2, FR-02). 소리 알림이 이 경우의 실질적 보완 수단 역할을 한다.

### EC-02. 탭 비활성화(백그라운드) 중 세션 종료
- 발생 조건: 브라우저 탭이 비활성 상태인 동안 세션의 종료 목표 시각이 지남
- 시스템 상태: 브라우저의 백그라운드 스로틀링으로 화면 갱신이 지연될 수 있음
- 사용자에게 표시되는 결과: 탭이 다시 활성화되는 즉시(visibilitychange) 종료 목표 시각과 현재 시각을 비교해 즉시 세션 종료 처리 및 알림/메모 입력 흐름 진행. 단, 이 보정은 탭 복귀 시점 기준의 정확한 상태 재계산을 의미하며, 백그라운드 상태에서의 실시간 알림 발생을 보장하는 것은 아니다.
- 데이터 처리: 실제 경과 시간은 절대시각 계산으로 정확히 유지되며, 화면 갱신 지연과 무관하게 데이터 정합성 영향 없음
- 재시도/복구/롤백 정책: 해당 없음 (자동 재계산으로 보정)
- 최종 상태: 탭 복귀 시점에 실제 시간 기준으로 정확히 보정된 상태

### EC-03. 새로고침 / 브라우저 재시작 시 진행 중이던 세션 복원 (다중 세션 만료 포함)
- 발생 조건: 타이머가 Running 또는 Paused 상태에서 새로고침 또는 브라우저 재시작 발생. 오프라인/종료 기간 동안 하나 이상의 세션이 만료되었을 수 있음
- 시스템 상태: localStorage에 저장된 진행 중 타이머 상태를 로드
- 사용자에게 표시되는 결과:
  - **Running으로 저장된 경우**: 종료 목표 시각이 아직 남아 있다면 복원된 세션과 남은 시간을 그대로 표시. 이미 지났다면, 경과한 세션 수와 무관하게 '중단 시점의 세션 1회만' 종료 처리(알림/메모 입력 포함)한 뒤 다음 세션을 Idle 상태로 대기시킨다(BR-02).
  - **Paused로 저장된 경우**: `endTimestamp`가 없으므로 만료 판단을 하지 않는다. 저장된 남은 시간 스냅샷을 그대로 Paused 상태로 복원한다(FR-08).
- 데이터 처리: Running 세션은 저장된 endTimestamp와 현재 시각을 비교하여 상태 재계산. 완료 처리된 세션의 로그는 원래 종료 목표 시각 기준 날짜로 귀속된다. Paused 세션은 별도 재계산 없이 스냅샷을 그대로 사용한다.
- 재시도/복구/롤백 정책: 해당 없음 (저장된 절대시각 기준 재계산 및 1회 종료 처리 규칙으로 항상 유효한 상태 도출)
- 최종 상태: Running이었던 세션은 이전과 동일한 진행 상태로 복귀하거나 '1회 종료 처리 + 다음 세션 Idle 대기'로 정리되고, Paused였던 세션은 오프라인 시간과 무관하게 동일한 남은 시간으로 복귀한다.

### EC-04. 시스템 시계(로컬 클록) 변경
- 발생 조건: 세션 시작·재개·탭 복귀(visibilitychange) 시점마다 `dateAnchor = Date.now()`와 `perfAnchor = performance.now()`를 함께 샘플링해 갱신한다. 이후 매 확인 시점(예: 화면 갱신 tick, 탭 복귀 등)마다 `dateDelta = Date.now() - dateAnchor`와 `perfDelta = performance.now() - perfAnchor`를 계산하고, `|dateDelta - perfDelta|`가 임계값(5초) 이상이면 시스템 시계 변경으로 판정한다. (두 API는 기준점(origin)이 다르므로 원시 값이 아닌 앵커 대비 델타끼리 비교한다. 앵커를 탭 복귀 시점마다 재설정하므로, 절전·백그라운드 동결 등으로 인한 정상적인 시간 경과는 재설정 직후 새로 측정되어 오탐지를 유발하지 않는다.)
- 시스템 상태: 해당 세션을 즉시 Paused 상태로 전환한다.
- 사용자에게 표시되는 결과: "시스템 시간 변경이 감지되어 타이머가 일시정지되었습니다"라는 확인 알림을 표시하고, 재개 버튼을 제공한다.
- 데이터 처리: 세션은 Paused 상태로 저장되며, 남은 시간은 이상 감지 직전 마지막으로 유효했던 계산값으로 고정된다. 임의로 시간을 연장하거나 단축하지 않는다.
- 재시도/복구/롤백 정책: 사용자가 재개를 선택하면 현재 시각을 기준으로 새 종료 목표 시각을 계산하고 앵커를 재설정하여 Running으로 전환한다. 사용자가 재개하지 않으면 Paused 상태로 유지된다.
- 최종 상태: 사용자 확인 후에만 타이머가 재개되며, 시계 변경으로 인한 임의의 시간 연장·단축 없이 안전하게 처리된 상태

### EC-05. localStorage 쓰기 실패
- 발생 조건: 저장 공간 초과, 브라우저 정책(예: 특정 시크릿 모드 제한) 등으로 localStorage 쓰기가 실패하는 경우
- 시스템 상태: 저장소 상태가 Write-Failed로 전환된다(6.2). 타이머 및 현재 세션 진행은 중단되지 않고 메모리 상에서 계속 동작한다.
- 사용자에게 표시되는 결과: "데이터가 저장되지 않고 있습니다 — 새로고침 시 최근 변경사항이 유실될 수 있습니다"라는 경고 배너를 화면에 표시한다.
- 데이터 처리: 실패한 쓰기는 이후 상태 변경 시점마다 자동으로 재시도한다. 재시도가 성공하면 저장소 상태를 Synced로 되돌리고 경고를 해제한다.
- 재시도/복구/롤백 정책: 자동 재시도만 수행하며, 별도의 수동 재시도 UI는 두지 않는다. 사용자 조작(타이머 시작 등)을 막지 않는다.
- 최종 상태: 저장이 재개되면 정상 상태로 복귀하고, 실패가 지속되는 동안은 경고가 표시된 채로 앱 사용은 계속 가능하다.

## 10. Non-Functional Requirements

### NFR-01. 타이머 정확도 (Reliability)
- 절대시각(Date.now()) 기반 계산 방식을 사용하여, OS 시스템 시계가 외부 요인으로 변경되지 않고 정상적으로 유지되는 동안에는 수 시간 이상 연속 구동해도 표시 시간과 실제 경과 시간 간 누적 오차(드리프트)가 발생하지 않아야 한다.
- 시스템 시계 변경 여부는 EC-04에 정의된 델타 비교 알고리즘(`Date.now()`와 `performance.now()`의 앵커 대비 델타 차이, 임계값 5초)으로 감지하며, 감지된 경우의 동작은 EC-04를 따른다.

### NFR-02. 오프라인 가용성 (Availability / Compatibility)
- 인터넷 연결이 전혀 없는 환경에서도 모든 기능이 정상 동작해야 한다.
- 외부 CDN, 웹폰트, 외부 API 등 네트워크 리소스에 의존하지 않아야 한다.

### NFR-03. 이식성 (Portability)
- 단일 HTML 파일만으로 배포·실행이 가능해야 하며, 별도의 설치나 서버 구동 없이 브라우저에서 파일을 여는 것만으로 동작해야 한다.
- §1.3에 명시된 지원 브라우저(Chrome/Edge/Firefox 최신 데스크톱 버전) 범위 내에서 이식성을 보장한다.

## 12. Technical Constraints & Approved Technical Decisions

### 12.1 Technical Constraints
- 단일 HTML 파일로 구현하며 서버를 사용하지 않는다.
- 완전 오프라인 동작을 위해 외부 네트워크 리소스(CDN, 웹폰트, 외부 API, 외부 음원 파일 등)를 일체 사용하지 않는다.
- 별도의 프레임워크(React 등)를 사용하지 않고 순수 HTML/CSS/JavaScript로 구현한다.
- 아이콘 등 그래픽 요소는 인라인 SVG로 구현한다.
- 지원 브라우저는 Chrome/Edge/Firefox 최신 데스크톱 버전(`file://` 실행 기준)으로 한정한다.

### 12.2 Approved Technical Decisions
- 타이머 계산 방식: `setInterval` 카운트다운이 아닌, `Date.now()` 기반 절대 종료 시각(endTimestamp) 계산 방식을 사용한다.
- 백그라운드 보정: Page Visibility API(`visibilitychange`)를 사용해 탭 비활성 후 복귀 시 즉시 상태를 재계산한다.
- 알림음: Web Audio API(OscillatorNode 등)로 소리를 직접 합성하며, 외부 음원 파일을 사용하지 않는다. 최초 사용자 상호작용 시점에 오디오 컨텍스트를 활성화한다.
- 브라우저 알림: Notification API를 사용하고, 권한이 허용된 경우 소리와 항상 동시 발송하며, 권한이 거부되었거나 API가 지원되지 않는 경우 소리 알림과 탭 제목 변경으로 대체한다. OS/브라우저 설정에 의한 알림 미표시는 감지 대상에서 제외한다.
- 데이터 저장: `localStorage`를 사용하며, 설정 / 일별 로그 / 진행 중 타이머 상태를 각각 별도 키로 분리 저장한다. 쓰기 실패 시 EC-05에 따라 경고 후 자동 재시도한다.
- 세션 흐름 제어: 상태 머신 방식으로 Focus / Short Break / Long Break 사이클을 관리하며, 세션 상태는 Idle/Running/Paused로 명시적으로 구분한다.
- 사이클 카운트: Focus 슬롯은 완료·스킵과 무관하게 소모되는 방식(슬롯 소모형)으로 4회차 Long Break 전환을 판단한다.
- 리셋 정책: 리셋은 현재 세션 타이머만 초기화하며, 사이클 슬롯 소모 카운트는 유지한다(BR-03).
- 자동 시작 범위: 세션 자동 시작은 실시간 사용 중(포그라운드 실행 중)에만 적용하며, 재접속으로 복원된 만료 세션은 자동 시작하지 않고 Idle로 대기시킨다(BR-02).
- **시스템 시계 변경 대응 알고리즘(승인된 결정, Implementation Freedom 제외 대상)**: 세션 시작·재개·탭 복귀 시점마다 `Date.now()`와 `performance.now()`를 앵커로 샘플링하고, 이후 각 클록의 앵커 대비 델타(`dateDelta`, `perfDelta`)를 비교하여 그 차이가 5초 이상이면 시계 변경으로 판정, 세션을 일시정지하고 사용자 확인 후 재개한다(EC-04). 원시 값의 직접 비교는 사용하지 않는다.
- 설정 적용 시점: Idle 세션은 설정 변경 즉시 반영, Running/Paused 세션은 해당 세션 종료 후 다음 세션부터 반영한다(FR-07).
- Memo-Input-Pending 상태에서는 타이머 제어 버튼(시작/일시정지/리셋/스킵)을 노출하지 않는다(BR-04).
- Paused 세션의 재접속 복원: endTimestamp 기반 만료 판단을 적용하지 않고 남은 시간 스냅샷을 그대로 복원한다(FR-08, EC-03).
- 오프라인 중 다중 세션 만료: 경과 세션 수와 무관하게 1회만 종료 처리한다.

### 12.3 Implementation Freedom
- 위에서 명시되지 않은 내부 구현 세부사항(클래스/함수/변수 명명, 내부 파일 구조, 완료 카운트·슬롯 소모의 저장 순서 등 세부 알고리즘, CSS 구조, 오디오 컨텍스트 활성화의 구체적 구현, Notification 권한 요청 시점 등)은 본 PRD의 승인된 내용을 위배하지 않는 한 Development AI가 합리적으로 결정할 수 있다.
- 세부 디자인과 UI(색상, 레이아웃, 애니메이션 등)는 사용자가 AI 재량으로 위임하였으므로, 위 기술 제약과 승인된 기술적 결정을 해치지 않는 범위 내에서 Development AI가 자유롭게 결정한다.
- **제외 사항**: 시스템 시계 변경 감지 알고리즘(EC-04, 12.2에 델타 비교 방식으로 명시됨)은 Implementation Freedom의 대상이 아니며, 다른 방식으로 대체할 수 없다.

## 13. Acceptance Criteria

### 13.1 Functional Acceptance
- FR-01 ~ FR-08에 정의된 모든 기능이 각 기능별 Acceptance Criteria를 충족한다.
- Paused 상태에서 새로고침/재접속해도 남은 시간 스냅샷이 오프라인 시간과 무관하게 그대로 복원된다(FR-08, EC-03).
- `Memo-Input-Pending` 상태에서는 타이머 제어 버튼이 노출되지 않고, 메모 제출/건너뛰기 UI만 노출된다(BR-04).
- Idle 세션의 설정 변경은 화면에 즉시 반영되고, Running/Paused 세션의 설정 변경은 다음 세션부터 반영된다(FR-07).
- localStorage 쓰기가 실패해도 타이머 사용이 중단되지 않고, 저장 실패를 알리는 경고가 표시된다(EC-05).

### 13.2 System Acceptance
- **정상 실행 중 시나리오**: 앱이 포그라운드에서 실행 중인 동안에는 타이머, 사이클 전환(자동 시작 포함), 스킵, 메모, 로그, 설정이 서로 연동되어 하나의 뽀모도로 세션 흐름(시작→종료→기록/자동전환→다음 세션)이 끊김 없이 동작한다.
- **재접속 복원 시나리오**: 앱이 종료되어 있던 동안 세션이 만료된 뒤 재접속한 경우, 정상 흐름과 달리 '1회 종료 처리 + 다음 세션 Idle 대기(수동 시작)'로 동작하며, 이는 BR-02에 따른 의도된 예외로 취급한다. Running/Paused 두 경우 모두 별도 테스트 케이스로 검증한다.
- 인터넷 연결 없이, 지원 브라우저에서 단일 HTML 파일을 여는 것만으로 위 흐름 전체가 정상 동작한다.

### 13.3 User Acceptance
- 사용자가 하루 동안 실제로 앱을 사용했을 때, 로그 화면에서 그날 완료한 뽀모도로 개수와 각 메모(빈 메모 포함)가 실제 작업 내역과 일치함을 확인할 수 있다.
- 사용자가 임의 시점에 새로고침하거나 브라우저를 재시작해도(앱이 다시 실행되는 시점을 기준으로) 진행 중이던 세션, 설정값, 로그가 그대로 유지됨을 확인할 수 있다.
- 브라우저가 실행 중이고 시스템 시계가 정상 유지되는 동안, 수 시간 이상 타이머를 켜둔 뒤에도 표시된 남은 시간이 실제 경과 시간과 일치함을 확인할 수 있다.
- 시스템 시계가 임의로 변경되면 타이머가 임의로 늘어나거나 줄어드는 대신 일시정지되고 확인을 요청받는다.
- 저장 공간 문제 등으로 데이터가 저장되지 않는 상황에서도, 사용자는 경고를 통해 이를 인지할 수 있다.
